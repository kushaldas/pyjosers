Encryption
==========

``JWE`` supports compact, flattened and general JSON serialization. Cryptography
and envelope policy run in Rust. Recipients are snapshotted by ``add_recipient``;
serialization or outgoing ``payload`` access encrypts the complete set once.
Cryptographic errors can therefore arise on serialization. Repeated serialization
reuses the envelope; adding a recipient invalidates it and generates a new one.

.. doctest::

   >>> from pyjosers import JWK, JWE
   >>> key = JWK.generate(kty="oct", alg="A256KW", use="enc")
   >>> message = JWE(b"confidential", protected={"alg": "A256KW", "enc": "A256GCM"}, recipient=key)
   >>> wire = message.serialize(compact=True)
   >>> received = JWE(algs=["A256KW", "A256GCM"])
   >>> received.deserialize(wire, key)
   >>> received.payload
   b'confidential'

``algs`` contains both key-management and content-encryption names. Pin expected
algorithms for each application. An empty allowlist disables operations. A JWK's
``alg`` pin cannot be overridden. A protected algorithm may bind an unpinned
compatibility key; an unprotected algorithm requires an existing trusted key pin.

Key management
----------------

``dir`` uses the octet key as the content key: GCM requires 128/192/256 bits;
CBC-HMAC requires 256/384/512 bits respectively. AES-KW and AES-GCMKW wrapping
keys require the bit size in their algorithm name. RSA-OAEP-256 uses public keys
for encryption and private keys for decryption. SHA-1 RSA-OAEP requires a legacy
build. IVs, tags and wrapping parameters are generated in Rust.

ECDH-ES and ECDH-ES+A128KW/A192KW/A256KW support P-256, P-384, P-521 and
X25519. Agreement keys require ``deriveKey`` permission. Protected ``apu`` and
``apv`` are base64url-encoded Concat KDF context. Each encryption uses fresh
ephemeral material. Key agreement provides confidentiality, not sender identity.

PBES2-HS256+A128KW, PBES2-HS384+A192KW and PBES2-HS512+A256KW accept explicit
string/bytes passwords; an octet JWK is not a password. ``pbes2_iterations``
defaults to 8,192 with a 1,000 minimum. ``pbes2_max_iterations`` defaults to
1,000,000 and can be lowered on each ``decrypt`` call. Salt and iteration header
members are generated by the backend; callers cannot inject them.

AAD, critical extensions and recipients
-----------------------------------------

JSON encryption accepts nonempty ``aad`` bytes. Decryption requires the same
bytes through ``expected_aad`` or the constructor's ``aad`` argument. AAD is
visible but authenticated. Compact serialization refuses external AAD.
``understood_crit`` declares private protected extensions implemented by the
application; it does not implement those extensions for you.

Repeated ``add_recipient`` calls produce general JSON with one ciphertext and
up to 32 wrapped keys. All recipients share one protected algorithm. AES-KW and
RSA transport support multiple recipients. ``dir``, GCMKW and PBES2 permit one;
ECDH modes use compact/flattened serialization only. ``flattened=False`` requests
general JSON even for a single recipient where supported.

``decrypt(key, recipient_index=...)`` selects explicitly. Otherwise a
multi-recipient message requires a unique recipient matching the trusted key's
``kid``. Duplicate or absent matches fail. Per-recipient emission supports
``kid`` only; arbitrary unprotected header emission is unsupported. Received
shared/per-recipient headers follow backend disjointness and pinning rules.
JWCrypto JSON output placing ephemeral or wrapping parameters unprotected is
intentionally refused; compact interoperability remains available.

Permissions, results and failures
-----------------------------------

Direct encryption checks ``encrypt``/``decrypt``; wrapping and RSA transport
check ``wrapKey``/``unwrapKey``. EC/X25519 agreement checks ``deriveKey``.
JWK Set selection is bounded using the policies described in :doc:`keys`.

``decrypt_authenticated`` returns an ``Authenticated`` result with ``value``,
``protected`` and separately labelled ``unprotected`` metadata. ``jose_header``
reports protected parameters and remains untrusted before decryption.
Failed decryption clears trusted plaintext and results; ``payload`` then raises.

``max_plaintext`` is an inclusive byte limit, including zero for empty messages;
``None`` retains the backend token-size limit. It applies to every decryption
serialization and preserves key/algorithm checks. CBC may require one extra
padding block before the exact authenticated length check.

Key-reference emission requires ``allow_key_reference_headers=True``. No URL is
fetched. Compression, RSA1_5 and PKCS#11 decryption are unsupported. See
:doc:`backend-0100` for the narrow empty-GCM JSON parser workaround.
